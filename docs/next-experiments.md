# Experiments after infrastructure validation

The generated corpus and verified reference traces establish that the benchmark can run and score its specified workflows. They do not establish agent capability or clinical realism. Treat these as separate experimental questions.

1. **Model baseline.** The first free source-based pilots are recorded in [training status](training-status.md). Extend the successful one-hop JSON-action curriculum to a stratified dev sample with varied codes, dates, statuses and identity ambiguity; preserve patient separation. Compare empty-answer, blind-gold-guess, scripted reference, broad retrieval and model policies. Report strict success, exact state delta, evidence coverage, ambiguity/absence behavior and calls/bytes. The reference solution is a ceiling check for the verifier, not a model baseline.
2. **FHIR fidelity.** Replay native R4 reference traces on an independent server and validate generated bundles with the official FHIR validator and relevant profiles. Replace the documented subset with an adapter to a real FHIR server before making interoperability claims. Add history, valid transitions, conditional operation semantics, paging fidelity, authorization and multi-valued search tests.
3. **SQL on FHIR.** Run actual portable ViewDefinitions through a conformant engine and check results against REST. Add complete array cardinality, multiple identifiers/code systems, SQL evidence lineage, absence-proof equivalence and snapshot consistency. Until then call our backend experimental SQLite projections. Evaluate same-task REST/hybrid call and data-transfer costs, without assuming SQL must win.
4. **Clinical expansion and review.** Vary episode topology, specialties, lab panels, diagnosis/documented-history distinction, reported versus confirmed medication, prescribing versus dispensing, external documents, longitudinal conflicts and omissions. Have clinical reviewers approve workflow families and a stratified sample of instances. Source notes currently provide realistic background; two task families use their explicit imported profile facts, while most scored gold lives in added fixtures. This must improve before calling the dataset a realistic general EHR workload.
5. **SFT then RL.** Collect source-training-only expert/model demonstrations and retain only verifier-passing trajectories. Warm up valid tool calls before RL. Start with retrieval depth <=2 and no efficiency penalty; then increase graph depth and write complexity. Evaluate at step 0 and fixed checkpoints. Add a small efficiency penalty only when strict correctness remains stable. Freeze curriculum/checkpoint choices before public/heldout evaluation.
6. **Analysis.** Log first target evidence, all required evidence including absence checks, sequential rounds, primitive operations, bytes, rows, model tokens, latency, cost, and structured query features. Failures are censored at budget. Report success-at-budget and success-conditioned cost; bootstrap by patient/source cluster. Plot actual checkpoint results beside preselected same-task query traces. Query length/joins are explanatory measures and receive no direct reward.
7. **Release.** Resolve generated-data/code license, include upstream/FHIR/LOINC notices, publish the data card and clinician review limitations, and reproduce wheel loading from a clean directory. Upload the environment with explicit v0 runtime; use the current native PrimeRL source-table schema and dedicated hosted eligibility checks. Small hosted pilots and public environment publication are recorded in training status; broader dedicated training and HF publication remain separate release steps.

Adaption Invent and Improve Data Quality were experimentally useful to evaluate a generation route, but vendor quality scores did not track our schema/semantic acceptability. Prefer deterministic world construction and verification, with generated wording/proposals accepted only through explicit compilation and review.
